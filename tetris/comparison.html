Tetris: generation 001 vs generation 002

All built from the same seed, tetris/spec.md, with pi. Generation 001 used the one-agent factory. Generation 002 used the three-machine factory, whose validator's lens was testability. The bonus round rebuilds generation 002 with the lens changed to single responsibility.

Verdict. Validation made a visible difference to the code's structure, and none to what the player gets.
  • Findings recorded: the validator raised 5 testability findings. All 5 were recorded in the plan as subtasks, and each one maps to a later commit that changed the code in the direction the finding asked for.
  • What changed: generation 002 exports its pieces, takes its terminal and starting state as inputs, and keeps the game logic pure.
  • What didn't: neither generation has a single test.
  • The biggest player-visible difference is unrelated to validation: in 002, pieces never fall on their own. Its plan never had a task for the game loop.

Differences supported by recorded validator findings

Every finding below is quoted from tetris/tetris-002/.factory/plan.md. The trace shows the pass that recorded each finding, the pass that addressed it, and the plan commit that marked it done.

Finding 1"src/index.js auto-starts on import and exports nothing, preventing side-effect-free unit tests."

Recorded under task 1 in 5814279. Addressed in 656ddaf, marked done in 8ea4101.

  • 001: index.js runs the game at module level (const game = new TetrisGame(), setRawMode, setInterval) and exports nothing.
  • 002: starts only under if (require.main === module), and exports 12 functions and 3 constants, including buildDisplay, actionForInput and createTetrisApp.
Finding 2"Terminal I/O is hard-coded to process.stdin/stdout instead of injectable streams, making behavior difficult to test."

Recorded under task 1 in 5814279. Addressed in 56e3635, marked done in f9a645e.

  • 001: writes straight to process.stdout and reads process.stdin throughout.
  • 002: createTerminalIO({ input, output }) wraps the streams, and createTetrisApp({ terminal, input, output, ... }) accepts a fake terminal.
Finding 3"Render and exit behavior are not exposed as isolated units, so output and cleanup cannot be tested directly."

Recorded under task 1 in 5814279. Addressed in b1b1dac, marked done in 1d8e960.

  • 001: draw() and stop() are private to index.js. Rendering is already separate in render.js, unprompted.
  • 002: render(), exit(), app.stop() and buildDisplay(state) are exported, and buildDisplay returns a string with no I/O.
Finding 4"start() creates a random initial state internally with no injection point, making startup rendering tests nondeterministic."

Recorded under task 2 in 656ddaf. Addressed in 3b333a2, marked done in acb7eb7.

  • 001: new TetrisGame({ random }) already accepts a random source, but index.js never passes one.
  • 002: resolveInitialState({ state, random, initialStateOptions, createState }) lets a caller fix the starting state or the randomness.
Finding 5"Several core helpers hard-code BOARD_WIDTH/BOARD_HEIGHT despite createBoard/createPiece accepting custom sizes, forcing large 10x20 fixtures and making focused unit tests harder."

Recorded under task 2 in 656ddaf. Addressed in 1f1f49d, marked done in 641a604.

  • 001: the class keeps this.width and this.height from its constructor, so small boards already work.
  • 002: helpers now read sizes from the board itself, through boardWidth(board), boardHeight(board) and boardDimensions(board).

How the findings flowed through the factory

  • Findings became their own passes. The doer recorded each finding as a subtask, but the passes that recorded them didn't fix them. The planner then marked the parent task done while its subtasks were still open, for example task 1 in c526660. Later passes picked the open subtasks up as "the first thing not done", one per pass. That's why generation 002 took 10 work passes for 5 tasks.
  • The plan stayed tidy. No finding became a new top-level task, as validation.feature requires.
  • Findings arrived early, then stopped. All 5 were raised on the first two tasks: setup and core game state. Tasks 3 to 5 (input, rendering, the 24-row limit) produced none. Either later work was more testable, or the validator found nothing new to say through this lens.

Differences with no recorded finding behind them

Two builds from the same seed differ anyway. Nothing in generation 002's plan explains these differences.

GameplayNo gravity in 002. Pieces only move when you press a key, so the game never speeds up or puts you under time pressure. stepGame handles a 'tick' action, but index.js has no timer, and the history shows it never had one. The cause is in the plan, not the validator. Generation 001's plan had "Implement keyboard controls and the game loop for interactive play", and generation 002's plan has no game-loop task. A testability lens wouldn't catch a missing feature.
ArchitectureGeneration 001 is an ES-module, class-based design with a separate render.js. Generation 002 is CommonJS with pure state-transition functions and everything else in one large index.js (289 lines). The pure stepGame reducer is easy to test, but no finding asked for it: it was written in the core game pass (656ddaf), before any finding about game.js existed.
Game rules
  • Randomizer: 001 draws pieces from a "7-bag", the standard shuffle of all seven pieces. 002 picks each piece uniformly at random, so droughts and repeats are possible.
  • Level: 001 shows one; 002 has none.
  • Scoring: both use 100, 300, 500 and 800 points for 1 to 4 lines.
Display and controls
  • Look: 001 draws coloured ██ blocks inside box-drawing borders, with the status above the board and a one-line control strip below. 002 draws piece letters on a dotted ASCII grid, with a side panel for score and controls.
  • Keys: 002 adds vim keys (h j k l). 001 also rotates on x.
  • Game over: 001 exits with a message. 002 shows GAME OVER in the panel and waits for q.
24-row limitBoth fit, in different ways:
  • 001 trims its output to exactly 24 lines.
  • 002 lays the panel beside the board for 22 lines and throws an error if a display would be taller. Its last task also added .npmrc with loglevel=silent, so npm's own banner doesn't take terminal rows.
These changes come from the seed's 24-row rule, not from a finding.

Bonus round: changing the lens

The same seed, model and factory, built into tetris/tetris-002-single-responsibility with the validator's lens set to single responsibility. The comparison is with tetris/tetris-002, the testability build.

Verdict. Changing the lens changed what the validator complained about, and the code's shape followed.
  • Testability asked for seams: exports, injectable I/O, a controllable starting state. The result was one big but injectable index.js of 289 lines.
  • Single responsibility asked for splits. The result was 10 small modules, the largest being gameplay.js at 135 lines.
  • Both lenses converged on similar seams. The single-responsibility build also ended up with an injectable terminal and a pure gameplay module, without being asked.
  • Fewer findings. The new lens raised 2 findings instead of 5, and the build took 7 passes instead of 10.

The planner never sees the lens. The two task lists differ the way any two plans from the same seed can. The second one happens to say "falling pieces", which is why that build has gravity and tetris-002 does not.

Differences supported by recorded findings

Finding 1"src/index.js has multiple responsibilities: board creation, display rendering, terminal I/O, input handling, and process lifecycle are all coupled in one module."

Recorded under task 1 in 67b3f01, where the split was already done. Follow-up in dc1f152, marked done in 6cc09e5.

  • The pass that raised it commits index.js at 5 lines, next to separate board.js, game.js, input.js, renderer.js and terminal.js. The coupled index.js the finding describes only existed in an attempt that was never committed.
  • The follow-up added cli.js (runTetrisCli({ terminal, exit })) and took process.exit out of game.js. The process lifecycle now lives in one place.
  • Contrast: under testability, index.js stayed the home of terminal I/O, input, rendering and the app lifecycle, at 289 lines.
Finding 2"src/tetrominoes.js mixes tetromino shape/movement responsibilities with board cell representation via ACTIVE_CELL and LOCKED_CELL."

Recorded under the gameplay task in ea8a078. Follow-up in a2ffde0, marked done in 09b7d8d.

  • The pass that raised it commits the cell constants in board.js, not tetrominoes.js. They had already moved once during the retries.
  • The follow-up moved them again, into their own cells.js, and changed their values from glyphs ('#') to names ('active', 'locked'). The renderer now maps names to glyphs, so how a cell looks belongs to the renderer alone.
  • Contrast: the testability build stores piece letters such as 'T' in the board and prints them directly.

Differences with no recorded finding behind them

Code and gameplay
  • Structure: 10 ES modules totalling 458 lines, against 2 CommonJS files totalling 630.
  • Gameplay: pieces fall every 500 ms. The plan asked for "falling pieces"; the testability build has no gravity.
  • A dependency: ansi-escapes, from the "add any helpful packages" task.
  • Display: one character per cell (#), a 10-column board, and score and controls below it, for 24 rows when played. The renderer trims the board if needed.
  • Fewer keys: arrows and w a s d, with no vim keys and no capitals.
  • Still no tests, as in both earlier generations.
FactoryThe last pass (91fb079) committed node_modules/, because the target has no .gitignore and the factory commits everything in the target. That's a rough edge in the factory, not a lens effect.

Caveats

  • One build each. Some of the "other" differences would change on a rebuild with the same factory and lens. The plans already differ between the two validated builds, and the lens can't explain that.
  • Testable is not tested. The findings are about seams: injection, exports and pure functions. Nobody asked for tests, so none were written. Testability improved on paper only.
  • Missing evidence. The factory doesn't keep the validator's raw answers or how many attempts each pass took. The plan's subtasks are the only record of findings.
